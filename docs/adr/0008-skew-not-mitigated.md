# ADR-0008. 스큐 대응 미적용 — 측정 결과 이득이 없어서

- 상태: Accepted
- 날짜: 2026-08 측정
- 프로젝트: VCC (별도 실험)

## 맥락

키워드와 카페 메뉴를 조인해 "유튜브에서 뜨는 키워드를 서울 카페들이 이미 얼마나 팔고 있나"를
집계하려 했다. 메뉴 분포가 롱테일이라(아메리카노는 거의 모든 카페에, 나머지는 희소)
조인·집계 키가 쏠린다. 교과서적으로는 broadcast join 과 salting 을 쓸 자리다.

**전제**: 이 조인 파이프라인은 프로젝트 당시 코드가 아니라 이후에 새로 만든 것이다.
서울시 공공데이터에 메뉴명 단위 데이터셋이 없어 합성 데이터를 썼다.

## 측정

키워드 6,494종 × 메뉴 1,296,229행. `local[*]`(16스레드), shuffle partitions 16, 각 3회 p50.

AQE 는 껐다. 켜두면 스큐를 자동 완화해서 salting 의 효과가 측정되지 않는다.
`plain` 은 `autoBroadcastJoinThreshold=-1` 로 자동 broadcast 를 꺼야 힌트와의 비교가 성립한다.

| 방식 | 조인 | 소요 p50 | 파티션 max/median |
|---|---|---|---|
| plain | SortMergeJoin | **44.44s** | 4.76 |
| broadcast | BroadcastHashJoin | 47.96s (+8%) | 4.76 |
| salting (상위 5키 × 16버킷) | BroadcastHashJoin | 62.03s (+40%) | **2.39** |

파티션 편차는 `mapPartitionsWithIndex` 로 파티션별 레코드 수를 직접 세서 얻었다.

## 결정

**둘 다 적용하지 않는다.**

- **broadcast**: `explain()` 상 SortMergeJoin → BroadcastHashJoin 으로 확실히 바뀌었다.
  바뀌었는데도 8% 느렸다. 키워드 쪽이 6,494행뿐이라 어느 방식이든 셔플이 지배적이지 않다.
- **salting**: 편차를 4.76 → 2.39 로 절반 줄였다. 효과는 실재한다.
  그런데 총 소요가 40% 늘었다. 2단계 집계에서 `collect_set` → `flatten` → `array_distinct`
  를 거치는 비용이 줄인 편차로 얻는 것보다 컸다.

**이 규모에서 스큐는 병목이 아니다.** 최대 파티션이 11만 행이어도 16스레드가 그걸
처리하는 시간은 전체에서 지배적이지 않다.

## 언제 다시 볼 것인가

- 파티션 편차가 수십 배로 커질 때 (지금은 4.8배)
- 파티션 하나가 executor 메모리를 넘겨 spill 이 날 때
- 단일 노드가 아니라 실제 클러스터로 갈 때 — 네트워크 셔플 비용이 커지면
  broadcast 의 이득이 여기보다 클 수 있다. **이 측정으로 "broadcast 는 쓸모없다"고
  일반화하면 틀린다.**

## 한계

합성 데이터의 쏠림(4.8배)이 실제 서울시 카페 메뉴 분포와 같다는 보장이 없다.
메뉴명 정규화도 konlpy 미설치 환경이라 정규식 폴백으로 돌렸다 (Okt 기준과 다를 수 있다).
