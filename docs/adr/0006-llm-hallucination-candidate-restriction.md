# ADR-0006. LLM 환각 대응 — 프롬프트 튜닝이 아닌 후보 선행 제한

- 상태: Accepted (수정 완료. **인과 주장은 A/B 로 반증됨** — 아래 "A/B 재측정")
- 날짜: 프로젝트 진행 중 결정 / 2026-09 측정
- 프로젝트: VCC

## 맥락

메뉴 추천을 LLM에 맡기자 원천 데이터에 없는 메뉴가 생성됐다. 그대로 Elasticsearch에
색인되면 "유튜브에서 추출한 트렌드"라는 파이프라인의 전제가 무너진다.
에러가 나지 않으니 조용히 섞인다는 점이 더 나빴다.

## 검토한 선택지

1. **프롬프트 튜닝** — "없는 걸 만들지 마라"를 더 강하게, 예시를 더 많이.
   기각: 모델이 바뀌거나 질문이 바뀌면 다시 깨진다. 지킬 근거가 프롬프트 문장뿐이다.
2. **생성 후 사후 필터** — 만든 다음 원천에 있는지 대조해 버린다.
   기각: 버릴 것을 만드는 비용을 매번 낸다. 다 버리면 답이 없다.
3. **후보 선행 제한 (채택)** — Neo4j에서 Cypher로 후보를 먼저 좁히고, 그 목록만
   프롬프트에 주입한다. 모델이 고를 수 있는 범위 자체를 줄인다.

## 결정

후보 선행 제한을 택했다. `graphrag_aq.py` 가 질문에서 태그·계절·카테고리를 뽑아
Cypher로 후보 10개를 조회하고, 그 목록과 함께 "이 키워드만 참고하라"는 제약을 준다.

## 결과 — 측정해보니 절반만 맞았다

2026-09, 저장된 답변 24건(생성 항목 112개)을 전수 검사했다 (`GragpRAG/eval_grounding.py`).

| 경로 | 생성 항목 | 후보 밖 |
|---|---|---|
| 메뉴 경로 | 92개 | **2개 (2.2%)** |
| 재료 경로 | 20개 | **10개 (50.0%)** |

*후보 밖 = 생성 이름에 후보 키워드가 하나도 들어가지 않은 경우(lenient).
완전 일치(strict) 기준으로는 70.5%이지만, 그 대부분은 후보를 조합한 결과라
이 프로젝트가 의도한 동작이다.*

메뉴 경로에서는 효과가 있었다. **재료 경로에서는 실패했다.**
후보 밖 값: 아보카도, 코코넛, 매실, 망고, 요거트, 고구마, `쿠알라룸푸르`.

### 50% 를 답변 단위로 풀면 — 비율이 숨긴 것

"절반쯤 샌다"로 읽히지만 항목이 아니라 **답변 단위**로 보면 그림이 다르다
(`python GragpRAG/eval_grounding_ab.py --historical`).

| 회차 | 후보 | 후보 밖 |
|---|---|---|
| 10차 | 크림, 초코, 딸기, 치즈, 우유, 커피, 녹차, 피넛 버터, 과일, 스폰지 | **5/5 (100%)** |
| 2025-04-30 | **위와 동일** | **0/5 (0%)** |
| 2025-05-03 | **위와 동일** | **0/5 (0%)** |
| 9ck | 위에서 과일·스폰지만 빠짐 | **5/5 (100%)** |

**전부 아니면 전무다.** 50% 는 절반씩 새는 것이 아니라
**답변 4건 중 2건이 통째로 무시한 것**이다. 그리고 결정적으로,
**같은 후보 목록이 100% 와 0% 를 둘 다 냈다.**

후보가 원인이라면 같은 후보에서 같은 결과가 나와야 한다. 갈린다는 것은
이 데이터만으로 **"후보가 나빠서 샜다"를 주장할 수 없다**는 뜻이다.
temperature 0.3 의 실행 간 분산이 더 그럴듯한 설명이다.

원인으로 지목했던 것은 **후보 자체**였다. 재료 경로의 Cypher는

```cypher
MATCH (i:Ingredient)
OPTIONAL MATCH (e:Example)-[:CONTAINS_INGREDIENT]->(i)
WITH i, count(e) AS usage_count
RETURN i.name AS keyword ORDER BY usage_count DESC LIMIT 10
```

겉보기엔 "사용 빈도 상위 10개"다. **그런데 `CONTAINS_INGREDIENT` 관계를 만드는 코드가
저장소 어디에도 없다.** `neo4j_schema.py` 가 생성하는 관계는 `RECORDED_ON`,
`HAS_CATEGORY`, `HAS_SEASON`, `HAS_TAG`, `IS_COMBO_WITH`, `INCLUDES`,
`HAS_EXAMPLE`, `RELATED` 8개뿐이다.

`OPTIONAL MATCH` 라서 에러는 나지 않는다. 대신 **모든 재료의 `usage_count` 가 0** 이 되고
`ORDER BY usage_count DESC` 가 전부 동점이 된다.

동점 정렬이 실제로 어떻게 동작하는지는 재 봤다 (10회 실행).

| | 옛 쿼리 |
|---|---|
| 정렬 키가 서로 다른 값 | 1종 (전부 0) |
| 10회 결과 집합 · 순서 | 각 **1종 (일정)** |

**실행마다 바뀌지 않는다.** 처음에 "정렬이 사실상 무작위"라고 적었으나 부정확했다.
저장 순서로 결정되고 그 순서는 안정적이다. 정확히는 **순위에 근거가 없다**.

이쪽이 더 나쁘다. 결과가 흔들렸다면 금방 드러났을 것이다.
**안정적으로** 질문과 무관한 답을 주기 때문에 프롬프트 문제로 오인된다.
질문은 "최근 **유행하는** 재료"인데 후보는 "저장 순서상 앞의 10개"다. 관계가 없으니
모델이 밖에서 끌어온다. **제약 문구로 막을 수 있는 종류의 문제가 아니었다.**

메뉴 경로가 잘 된 이유가 여기서 대비된다. 그쪽은 `HAS_TAG`·`HAS_SEASON`·`HAS_CATEGORY`
— **실재하는 관계** 를 타고 `k.count` 로 정렬한다. 후보가 질문(단맛/비주얼/트렌디)과
축이 맞는다. 같은 제약 문구인데 결과가 23배 갈린 것은 프롬프트 차이가 아니라
**후보 쿼리가 실제로 동작하느냐 아니냐**의 차이였다.

## 배운 것

**후보 선행 제한은 "후보가 질문에 답이 될 때만" 작동한다.**
제약을 거는 것과 제약 안에 답이 있게 만드는 것은 다른 일이다.

그리고 더 실무적인 교훈이 하나 더 있다.
**`OPTIONAL MATCH` 는 없는 관계를 조용히 0으로 만든다.** 쿼리는 성공하고,
결과도 10개가 나오고, 아무도 에러를 보지 못한다. 그래서 1년 넘게 드러나지 않았다.
후보 밖 생성률을 세어보고 나서야 역추적으로 찾았다.

**측정이 없었으면 프롬프트를 고치고 있었을 것이다.** 실제 원인은 Cypher 였다.

## 이번에 넣은 것 — 런타임 격리

측정만으로는 다음 회차에 같은 일이 또 난다. 생성 직후에 잡도록 검증을 넣었다.

- `GragpRAG/grounding.py` — 후보 안/밖 판정의 **단일 출처**.
  `graphrag_aq.py`(런타임 격리)와 `eval_grounding.py`(사후 측정)가 같은 모듈을 쓴다.
  둘이 각자 판정을 들고 있으면 기준이 갈라져 둘 다 못 믿게 된다.
- `graphrag_aq.py` — 파싱 실패뿐 아니라 **후보 밖 응답도** `data/graphrag_dead_letter.jsonl`
  로 격리하고 사유별 건수를 출력한다. 예전에는 `print` 후 건너뛰어서
  "스키마 실패율"조차 낼 수 없었다.

판정은 **lenient**(부분 문자열 포함) 기준이다. 이 프로젝트는 후보를 조합해 새 이름을
만드는 것이 의도된 동작이라 strict 를 쓰면 정상 결과가 전부 격리된다(실측 70.5%).

## 고친 것 — 후보 쿼리 교체

실재하는 관계만 쓰도록 바꿨다. 재료는 `Combo` 를 통해서만 `Keyword` 와 이어진다.

```cypher
MATCH (i:Ingredient)<-[:INCLUDES]-(:Combo)<-[:IS_COMBO_WITH]-(k:Keyword)
OPTIONAL MATCH (k)-[:RECORDED_ON]->(d:Date)
WITH i, max(d.value) AS latest, sum(k.count) AS freq
RETURN i.name AS keyword ORDER BY latest DESC, freq DESC LIMIT $limit
```

"최근 유행하는" 이라는 질문에 맞춰 **최근 기록일이 1순위, 언급 빈도 합이 2순위**다.
누적 `count` 만으로 정렬하면 "많이 나온 것"이지 "뜨는 것"이 아니다.

실제 Neo4j 로 확인한 전/후 (`GragpRAG/eval_candidates.py`).
측정 조건: 2025-05-03 데이터 **1회 적재**, Ingredient 98개(고아 0개), 각 10회 실행.

| | 상위 5개 | 정렬 키 |
|---|---|---|
| 전 | 밀가루, 버터, 크림, 빵, 그릭 요거트 | 전부 **0** |
| 후 | **딸기(209), 크림(208), 초콜릿(183), 생크림(130), 소금(124)** | 서로 다른 값 10종 |

후보에서 빠진 것은 `밀가루`·`버터`·`과일`·`견과류`·`그릭 요거트` 5개이고,
앞의 넷은 어떤 `Combo` 에도 속하지 않는 일반 재료다.

`count` 가 누적되므로 **적재 횟수가 `freq` 를 바꾼다** (2회 적재 시 딸기 209 → 418 실측).
스크립트가 `Date` 노드 수로 회차를 세서 1회가 아니면 경고한다.

**여기서 잰 것은 후보 목록이지 후보 밖 생성률이 아니다.** 생성률 재측정에는
OpenAI 키가 필요하고 아직 하지 않았다. 아래 "상태"를 참조.

후보가 비면 LLM 이 제약 없이 생성하므로 폴백도 넣었다 (Combo 미적재 회차 대비).

쿼리를 `GragpRAG/candidates.py` 로 분리했다. `graphrag_aq.py` 는 import 만 해도
Neo4j·OpenAI 가 붙어 테스트할 수 없었다. 후보 선정은 이 파이프라인에서 가장 틀리기
쉬운 자리라 검증 가능한 자리에 둬야 한다.

`tests/test_candidates.py` 8개가 실제 Neo4j 픽스처로 검증한다.
그중 **고아 재료 제외** 테스트가 이 회귀를 실제로 잡는다 —
깨진 쿼리로 되돌려 2개 실패하는 것을 확인했다.

> 순위 검증만으로는 부족하다. 깨진 쿼리에서도 순위 테스트가 통과했다
> (전부 동점이라 저장 순서가 우연히 기대와 맞았다).
> **"조용히 임의가 되는" 버그는 순위가 아니라 집합으로 잡아야 한다.**

## A/B 재측정 — 인과 주장이 성립하지 않는다

`graphrag_aq.py` 를 다시 돌려도 모델·시점이 달라 기존 50% 와 직접 비교할 수 없다.
그래서 **같은 실행 안에서 후보 목록만 바꿔** 두 팔을 돌렸다
(`GragpRAG/eval_grounding_ab.py`). 모델·temperature·프롬프트·질문·반복 수는 동일하다.

### 실측

| 조건 | 모델 | 답변 | 항목 | 후보 밖 |
|---|---|---|---|---|
| 재료 old / new | gpt-4o-mini | 4 / 4 | 20 / 20 | **0 / 0** |
| 메뉴 old / new (통제군) | gpt-4o-mini | 20 / 20 | 100 / 100 | 0 / 0 |
| 재료 old / new | **gpt-4** | 4 / 4 | 20 / 20 | **0 / 0** |
| 메뉴 old / new (통제군) | **gpt-4** | 20 / 20 | 100 / 99 | 0 / 1 |

옛 쿼리의 출력이 적재마다 달라지므로(아래) **적재를 5회 새로 하며** 재료 경로만 반복했다.

| 적재 | 옛 후보 상위 3 | old | new |
|---|---|---|---|
| 1 | 고소한 국물, 가나슈, 캔디 | 0/15 | 0/15 |
| 2 | 찰떡, 트러플, 찹쌀떡 | 0/15 | 0/15 |
| 3 | 찰떡, 트러플, 찹쌀떡 | 0/15 | 0/15 |
| 4 | 노스 카나 겔, 멜로 딸기, 쫀득한 식감 | 0/13 | 0/15 |
| 5 | 노스 카나 겔, 멜로 딸기, 쫀득한 식감 | 0/14 | 0/15 |

**gpt-4 로 5개 적재 × 3회 × 2팔, 위반 0건.** 엉터리 후보를 줘도 벗어나지 않았다.

### 결론

**"후보를 고쳐서 환각이 줄었다"는 주장은 세울 수 없다.** 근거가 둘이다.

1. 역사적 데이터에서 **같은 후보 목록이 100% 와 0% 를 둘 다 냈다** (위 표).
2. 새 측정에서 **옛 후보로도 위반이 0건**이다 (gpt-4 30답변, gpt-4o-mini 24답변).

50% 는 답변 4건 중 2건이 통째로 무시한 것이고, N 이 4 다.
이 크기에서 비율을 인과의 근거로 쓰면 안 된다.

### 그럼 수정은 왜 유지하는가

**환각과 무관하게 옛 쿼리가 틀렸기 때문이다.** 근거는 별도로 측정했다.

- 정렬 키(`usage_count`)가 **전부 0** 이라 순위에 근거가 없다
- 존재하지 않는 관계를 조회한다 (`db.relationshipTypes()` 에 없음)
- 출력이 **적재마다 바뀐다** — 위 표에서 5회 적재가 3가지 목록을 냈다.
  한 적재 안에서는 10회 모두 같지만, 다시 적재하면 달라진다.
  물리적 저장 순서에 의존한다는 뜻이다

"최근 유행하는 재료"를 물었는데 저장 순서 상위 10개를 주는 것은
환각이 나든 안 나든 잘못된 동작이다. 수정 근거는 여기에 있지, 생성률에 있지 않다.

## 남은 일

**재료 경로 위반을 재현할 조건을 모른다.** 새 측정 54개 답변에서 한 건도 안 나왔다.
역사적 2건이 어떤 조건에서 나왔는지 특정하지 못했다 — 모델 스냅샷 변경,
그때의 그래프 상태, temperature 분산 중 무엇인지 가릴 데이터가 없다.

재현 조건을 못 찾으면 이 실패 모드는 **감시 대상**으로만 남길 수밖에 없다.
`grounding.validate_answer` 가 런타임에 격리하고 있으므로 유출은 막힌다.

`RECORDED_ON` 이 현재 1개 날짜뿐이라 최근일 정렬이 실질적으로 작동하지 않는다.
회차가 쌓이면 의미가 생긴다. 회차가 여럿 쌓인 뒤 재측정해 후속 ADR 로 남긴다.

그래프 스키마 전체는 [docs/architecture/data-model.md](../architecture/data-model.md) 참조.
