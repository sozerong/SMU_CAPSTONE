# ADR-0006. LLM 환각 대응 — 프롬프트 튜닝이 아닌 후보 선행 제한

- 상태: Accepted (원인 규명 후 수정 완료 — 아래 "고친 것" 참조)
- 날짜: 프로젝트 진행 중 결정 / 2026-09 측정
- 프로젝트: VCC

## 맥락

메뉴 추천을 LLM에 맡기자 원천 데이터에 없는 메뉴가 생성됐다. 그대로 Elasticsearch에
색인되면 "유튜브에서 추출한 트렌드"라는 파이프라인의 전제가 무너진다.
에러가 나지 않으니 조용히 섞인다는 점이 더 나빴다.

## 검토한 선택지

1. **프롬프트 튜닝** — "없는 걸 만들지 마라"를 더 강하게, 예시를 더 많이.
   기각: 모델이 바뀌거나 질문이 바뀌면 다시 깨진다. 지킬 근거가 프롬프트 문장뿐이다.
2. **생성 후 사후 필터** — 만든 다음 원천에 있는지 대조해 버린다.
   기각: 버릴 것을 만드는 비용을 매번 낸다. 다 버리면 답이 없다.
3. **후보 선행 제한 (채택)** — Neo4j에서 Cypher로 후보를 먼저 좁히고, 그 목록만
   프롬프트에 주입한다. 모델이 고를 수 있는 범위 자체를 줄인다.

## 결정

후보 선행 제한을 택했다. `graphrag_aq.py` 가 질문에서 태그·계절·카테고리를 뽑아
Cypher로 후보 10개를 조회하고, 그 목록과 함께 "이 키워드만 참고하라"는 제약을 준다.

## 결과 — 측정해보니 절반만 맞았다

2026-09, 저장된 답변 24건(생성 항목 112개)을 전수 검사했다 (`GragpRAG/eval_grounding.py`).

| 경로 | 생성 항목 | 후보 밖 |
|---|---|---|
| 메뉴 경로 | 92개 | **2개 (2.2%)** |
| 재료 경로 | 20개 | **10개 (50.0%)** |

*후보 밖 = 생성 이름에 후보 키워드가 하나도 들어가지 않은 경우(lenient).
완전 일치(strict) 기준으로는 70.5%이지만, 그 대부분은 후보를 조합한 결과라
이 프로젝트가 의도한 동작이다.*

메뉴 경로에서는 효과가 있었다. **재료 경로에서는 실패했다.**
후보 밖 값: 아보카도, 코코넛, 매실, 망고, 요거트, 고구마, `쿠알라룸푸르`.

원인은 프롬프트가 아니라 **후보 자체**였다. 재료 경로의 Cypher는

```cypher
MATCH (i:Ingredient)
OPTIONAL MATCH (e:Example)-[:CONTAINS_INGREDIENT]->(i)
WITH i, count(e) AS usage_count
RETURN i.name AS keyword ORDER BY usage_count DESC LIMIT 10
```

겉보기엔 "사용 빈도 상위 10개"다. **그런데 `CONTAINS_INGREDIENT` 관계를 만드는 코드가
저장소 어디에도 없다.** `neo4j_schema.py` 가 생성하는 관계는 `RECORDED_ON`,
`HAS_CATEGORY`, `HAS_SEASON`, `HAS_TAG`, `IS_COMBO_WITH`, `INCLUDES`,
`HAS_EXAMPLE`, `RELATED` 8개뿐이다.

`OPTIONAL MATCH` 라서 에러는 나지 않는다. 대신 **모든 재료의 `usage_count` 가 0** 이 되고
`ORDER BY usage_count DESC` 는 전부 동점이라 **정렬이 사실상 무작위**가 된다.

즉 이 쿼리는 상위 10개가 아니라 **임의의 재료 10개**를 준다.
질문은 "최근 **유행하는** 재료"인데 후보는 무작위다. 질문과 아무 관계가 없으니
모델이 밖에서 끌어온다. **제약 문구로 막을 수 있는 종류의 문제가 아니었다.**

메뉴 경로가 잘 된 이유가 여기서 대비된다. 그쪽은 `HAS_TAG`·`HAS_SEASON`·`HAS_CATEGORY`
— **실재하는 관계** 를 타고 `k.count` 로 정렬한다. 후보가 질문(단맛/비주얼/트렌디)과
축이 맞는다. 같은 제약 문구인데 결과가 23배 갈린 것은 프롬프트 차이가 아니라
**후보 쿼리가 실제로 동작하느냐 아니냐**의 차이였다.

## 배운 것

**후보 선행 제한은 "후보가 질문에 답이 될 때만" 작동한다.**
제약을 거는 것과 제약 안에 답이 있게 만드는 것은 다른 일이다.

그리고 더 실무적인 교훈이 하나 더 있다.
**`OPTIONAL MATCH` 는 없는 관계를 조용히 0으로 만든다.** 쿼리는 성공하고,
결과도 10개가 나오고, 아무도 에러를 보지 못한다. 그래서 1년 넘게 드러나지 않았다.
후보 밖 생성률을 세어보고 나서야 역추적으로 찾았다.

**측정이 없었으면 프롬프트를 고치고 있었을 것이다.** 실제 원인은 Cypher 였다.

## 이번에 넣은 것 — 런타임 격리

측정만으로는 다음 회차에 같은 일이 또 난다. 생성 직후에 잡도록 검증을 넣었다.

- `GragpRAG/grounding.py` — 후보 안/밖 판정의 **단일 출처**.
  `graphrag_aq.py`(런타임 격리)와 `eval_grounding.py`(사후 측정)가 같은 모듈을 쓴다.
  둘이 각자 판정을 들고 있으면 기준이 갈라져 둘 다 못 믿게 된다.
- `graphrag_aq.py` — 파싱 실패뿐 아니라 **후보 밖 응답도** `data/graphrag_dead_letter.jsonl`
  로 격리하고 사유별 건수를 출력한다. 예전에는 `print` 후 건너뛰어서
  "스키마 실패율"조차 낼 수 없었다.

판정은 **lenient**(부분 문자열 포함) 기준이다. 이 프로젝트는 후보를 조합해 새 이름을
만드는 것이 의도된 동작이라 strict 를 쓰면 정상 결과가 전부 격리된다(실측 70.5%).

## 고친 것 — 후보 쿼리 교체

실재하는 관계만 쓰도록 바꿨다. 재료는 `Combo` 를 통해서만 `Keyword` 와 이어진다.

```cypher
MATCH (i:Ingredient)<-[:INCLUDES]-(:Combo)<-[:IS_COMBO_WITH]-(k:Keyword)
OPTIONAL MATCH (k)-[:RECORDED_ON]->(d:Date)
WITH i, max(d.value) AS latest, sum(k.count) AS freq
RETURN i.name AS keyword ORDER BY latest DESC, freq DESC LIMIT $limit
```

"최근 유행하는" 이라는 질문에 맞춰 **최근 기록일이 1순위, 언급 빈도 합이 2순위**다.
누적 `count` 만으로 정렬하면 "많이 나온 것"이지 "뜨는 것"이 아니다.

실제 Neo4j(2025-05-03 데이터, Ingredient 98개)로 확인한 전/후:

| | 상위 5개 |
|---|---|
| 전 | 밀가루, 버터, 크림, 빵, 그릭 요거트 — `usage_count` 전부 **0** |
| 후 | **딸기(209), 크림(202), 초콜릿(179), 소금(124), 생크림(112)** |

후보가 비면 LLM 이 제약 없이 생성하므로 폴백도 넣었다 (Combo 미적재 회차 대비).

쿼리를 `GragpRAG/candidates.py` 로 분리했다. `graphrag_aq.py` 는 import 만 해도
Neo4j·OpenAI 가 붙어 테스트할 수 없었다. 후보 선정은 이 파이프라인에서 가장 틀리기
쉬운 자리라 검증 가능한 자리에 둬야 한다.

`tests/test_candidates.py` 8개가 실제 Neo4j 픽스처로 검증한다.
그중 **고아 재료 제외** 테스트가 이 회귀를 실제로 잡는다 —
깨진 쿼리로 되돌려 2개 실패하는 것을 확인했다.

> 순위 검증만으로는 부족하다. 깨진 쿼리에서도 순위 테스트가 통과했다
> (전부 동점이라 저장 순서가 우연히 기대와 맞았다).
> **"조용히 임의가 되는" 버그는 순위가 아니라 집합으로 잡아야 한다.**

## 남은 일

`RECORDED_ON` 이 현재 1개 날짜뿐이라 최근일 정렬이 실질적으로 작동하지 않는다.
회차가 쌓이면 의미가 생긴다. 회차가 여럿 쌓인 뒤 재측정해 후속 ADR 로 남긴다.
