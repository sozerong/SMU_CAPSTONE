# 운영 지표와 SLO — VCC

## 이 문서가 목표치를 정하는 방법

SLO 를 "이 정도면 괜찮다"로 정하면 아무것도 판정하지 못한다. 근거가 취향이기 때문이다.
여기서는 **목표치를 시스템에 이미 존재하는 제약에서 뽑아낸다.** 출처는 넷뿐이다.

| 근거 유형 | 뜻 | 예 |
|---|---|---|
| **A. 선언된 값** | 코드에 이미 박혀 있는 설정 | `sorted_phrases[:500]` |
| **B. 플랫폼 상수** | 내가 바꿀 수 없는 한계 | — (이 저장소에는 해당 없음) |
| **C. 정합성** | 튜닝 대상이 아님. 1건이라도 틀리면 버그 | 회차 삭제 후 잔여 0 |
| **D. 대조군** | 같은 조건의 다른 선택지를 이겨야 함 | LLM 없는 정렬, 메뉴 경로 |

**목표치를 못 세우는 항목은 목표를 쓰지 않는다.** 이 저장소는 그런 항목이 많다.
LLM 3단계가 비결정적이고 배치 TF-IDF 가 코퍼스에 의존하기 때문이다.

튜닝할 값이 아니라 버그다. 반면 그 아래 "회차 간 재현성"은 입력이 서로 달라
목표를 세울 대상이 아니다 — 둘은 다른 질문이고 표에서도 분리한다.

## D. 대조군 — 목표가 다른 선택지인 것

### 정제 필터: LLM 이 정렬을 이겨야 한다 ✅

"정밀도 80% 이상" 같은 목표는 근거가 없다. 대신 **LLM 을 빼 보면** 근거가 생긴다.

`food_fillter.py` 는 후보 322개를 `score_priority` 로 정렬해 LLM 에 넘기고 49개를 받는다.
LLM 을 빼고 **같은 정렬의 상위 49개**를 쓰면 얼마인가? 출력 개수가 같으니 공평한 대조다.
LLM 이 이걸 못 넘기면 API 비용과 비결정성을 지불할 근거가 없다.

```bash
python agent/eval_filter.py baseline
```

| | 정밀도 |
|---|---|
| 기준선 (LLM 없이 점수 상위 49) | **6.1%** (층화 추정, 메뉴 3.0개/49) |
| LLM 필터 | **57.1%** (28/49, 95% CI 43.3~70.0%) |
| 차이 | **+51.0%p** |

LLM 신뢰구간 하한 43.3% 가 기준선 6.1% 를 한참 넘는다. **LLM 단계는 값을 한다.**

기준선이 왜 이렇게 낮은가가 더 중요하다. 점수 상위 49개는 `리얼 사운드`(24),
`에어 프라이어`(18), `리얼`(12), `사운드`(12) 처럼 **빈도만 높은 콘텐츠성 단어**로 채워진다.
빈도 정렬은 "많이 나온 말"을 고르지 "메뉴"를 고르지 않는다.

> 추정 방식: 상위 49개를 ①LLM 도 고른 것(6개, 전수 라벨) ②LLM 이 버린 것(43개, 표본 18개)
> 두 층으로 나눠 층별 비율을 가중 합산했다. ②의 표본이 18개라 기준선은 흔들릴 수 있다.
> 다만 ②에서 메뉴가 **0개**라 층화 없이 봐도 결론은 바뀌지 않는다.

### 재료 경로 후보 밖 생성률 — A/B 로 인과가 반증됐다

이 목표는 **같은 저장소 안의 내부 대조군**에서 나온다. 두 경로는 같은 코드,
같은 모델(gpt-4, temperature 0.3), 거의 같은 제약 문구를 쓴다.
조건이 같으므로 결과도 같아야 하고, 다르면 프롬프트가 아닌 다른 원인이 있다.

| 경로 | 답변 | 생성 항목 | 후보 밖(lenient) |
|---|---|---|---|
| 메뉴 경로 (대조군) | 20건 | 92개 | 2.2% |
| 재료 경로 | 4건 | 20개 | **50.0%** |

23배 차이를 Cypher 버그 탓으로 지목했었다. 그 주장을 A/B 로 검증했다.

#### 50% 를 답변 단위로 풀면

```bash
python GragpRAG/eval_grounding_ab.py --historical
```

| 회차 | 후보 | 후보 밖 |
|---|---|---|
| 10차 | 크림, 초코, 딸기, 치즈, 우유, 커피, 녹차, 피넛 버터, 과일, 스폰지 | **5/5 (100%)** |
| 2025-04-30 | **동일** | **0/5 (0%)** |
| 2025-05-03 | **동일** | **0/5 (0%)** |
| 9ck | 과일·스폰지만 빠짐 | **5/5 (100%)** |

**절반씩 새는 것이 아니라 전부 아니면 전무다.** 답변 4건 중 2건이 통째로 무시했다.
그리고 **같은 후보 목록이 100% 와 0% 를 둘 다 냈다.**
후보가 원인이라면 같은 후보에서 같은 결과가 나와야 한다.

#### A/B — 후보만 바꾼다

기존 50% 는 gpt-4 로 잰 값이다. 다른 모델로 다시 재면 차이가 Cypher 때문인지
모델 때문인지 구분할 수 없다. 그래서 **같은 실행 안에서 후보 목록만 바꿔** 두 팔을 돌린다
(`GragpRAG/eval_grounding_ab.py`). 메뉴 경로는 수정 대상이 아니라 통제군이 된다.

| 조건 | 모델 | 답변 | 항목 | 후보 밖 |
|---|---|---|---|---|
| 재료 old / new | gpt-4o-mini | 4 / 4 | 20 / 20 | **0 / 0** |
| 메뉴 old / new | gpt-4o-mini | 20 / 20 | 100 / 100 | 0 / 0 |
| 재료 old / new | **gpt-4** | 4 / 4 | 20 / 20 | **0 / 0** |
| 메뉴 old / new | **gpt-4** | 20 / 20 | 100 / 99 | 0 / 1 |

옛 쿼리 출력이 적재마다 달라지므로 **적재를 5회 새로 하며** 재료 경로만 반복했다.
gpt-4 로 5적재 × 3회 × 2팔, **위반 0건.** 엉터리 후보를 줘도 벗어나지 않았다.

#### 결론

**"후보를 고쳐서 환각이 줄었다"는 주장은 세울 수 없다.**
역사적 데이터에서 같은 후보가 상반된 결과를 냈고, 새 측정에서는 옛 후보로도 위반이 0건이다.
50% 의 N 은 답변 4건이다. 이 크기에서 비율을 인과의 근거로 쓰면 안 된다.

**그래도 수정은 유지한다.** 환각과 무관하게 옛 쿼리가 틀렸기 때문이다 — 아래 참조.
자세한 근거는 [ADR-0006](adr/0006-llm-hallucination-candidate-restriction.md).

### 대신 잰 것 — 후보 목록의 품질

생성률은 못 재도 그 **입력**은 Neo4j 만으로 잰다 (`GragpRAG/eval_candidates.py`).
2025-05-03 데이터 1회 적재, Ingredient 98개(고아 0개), 각 쿼리 10회 실행.

| | 전 | 후 |
|---|---|---|
| 상위 5 | 밀가루, 버터, 크림, 빵, 그릭 요거트 | 딸기(209), 크림(208), 초콜릿(183), 생크림(130), 소금(124) |
| 정렬 키가 서로 다른 값 | **1종 (전부 0)** | 10종 |
| 10회 결과 집합·순서 | 각 1종 | 각 1종 |
| `CONTAINS_INGREDIENT` 존재 | `db.relationshipTypes()` 에 **없음** | 사용 안 함 |

**옛 쿼리도 결과는 일정했다.** "정렬이 무작위가 된다"는 부정확한 서술이었고,
정확히는 순위에 근거가 없어 저장 순서로 고정된다는 것이다.
안정적으로 질문과 무관한 답을 주므로 프롬프트 문제로 오인되기 쉽다.

**수정을 유지하는 근거가 여기에 있다.** 환각이 나든 안 나든 옛 쿼리는 틀렸다.

- 정렬 키가 전부 0 이라 순위에 근거가 없다
- 존재하지 않는 관계를 조회한다
- **출력이 적재마다 바뀐다** — A/B 에서 5회 적재가 3가지 목록을 냈다
  (`밀가루·버터…` / `찰떡·트러플…` / `노스 카나 겔·멜로 딸기…`).
  한 적재 안에서는 10회 모두 같지만 다시 적재하면 달라진다. 물리적 저장 순서에 의존한다.

"최근 유행하는 재료"를 물었는데 저장 순서 상위 10개를 주는 것은 그 자체로 잘못된 동작이다.

> `Keyword.count` 가 누적되므로 **적재 횟수가 `freq` 를 바꾼다** (2회 적재 시 딸기 209 → 418).
> 스크립트가 `Date` 노드 수로 회차를 세서 1회가 아니면 경고한다.

## C. 정합성 — 목표가 0 인 것들

튜닝 대상이 아니다. **1건이라도 발생하면 성능 문제가 아니라 버그다.**

| 지표 | 왜 0 이어야 하는가 | 실측 |
|---|---|---|
| 회차 삭제 후 잔여 | 남으면 "이번 주 트렌드"가 과거와 섞인다 | 712노드 적재 → `delete-round` 1회 → **0** |
| 회차 태그 없는 Keyword | `RECORDED_ON` 이 없으면 **영원히 지울 수 없다** | 337개 중 251개(74%) → **0** |
| `count` NULL 오염 | `NULL + n = NULL` 이라 한 번 되면 영구적. 정렬에서 계속 밀린다 | `coalesce` 적용 후 **0** |
| 답변 파싱 실패 유실 | 파싱 실패를 버리면 몇 건이 사라졌는지도 모른다 | dead letter 격리 + 집계 |
| Spark 잡 재실행 일치 | 같은 입력에 다른 답이 나오면 뒤 단계의 측정이 전부 무의미해진다 | 3코퍼스 18회 → **전부 일치** |

`RECORDED_ON` 과 `count` 두 건은 **정리 수단을 만들다가 발견한 것**이다.
`cleanup.py` 를 쓰기 전에는 지울 수 없는 노드가 쌓이는 줄 몰랐다.

## 목표를 세울 수 없는 것

이 저장소에서 가장 중요한 절이다. **목표를 세우면 거짓말이 되는 항목들이다.**

### 재현성 — 구조적으로 보장 불가 (단 원인은 Spark 가 아니다)

"같은 파이프라인을 N회 돌리면 같은 결과"는 이 구조에서 주장할 수 없다.
**결론은 유지되지만 원인의 소재는 측정으로 좁혀졌다.** 세 겹으로 나눠 쓴다.

**① LLM 3단계가 비결정적이다.** temperature 0.3 / 0.2 / 0.3, 캐시도 시드도 없다.
이것만으로 파이프라인 전체의 재현성 목표는 설 자리가 없다.

**② Spark 잡 자체는 같은 입력에서 결정적이다.**

Kafka 토픽에 **한 번만** 주입하고 `spark_keyword.py` 를 N회 재실행했다
(`kafka/replay_to_kafka.py` + `verify_reproducibility.py run`).

| 주입 파일 | 문서 | 재실행 | 완전 일치 | 산출물 digest |
|---|---|---|---|---|
| `data/8차/keywords.jsonl` | 575 | 10회 | 575/575 (**100%**) | `ef6c1262bb2a3ae4` |
| `data/2025-05-03/keywords.jsonl` | 1,105 | 5회 | 1105/1105 (**100%**) | `535e0178e718e8fa` |
| 8차 + 05-03 신규 790건 | 1,365 | 3회 | 1365/1365 (**100%**) | `7789335fed5d7e95` |

**18회 전부 일치했다.** 순서만 다른 건수도 0이다. 토픽을 지우고 같은 파일로 다시
주입해도 digest 가 같았으므로, "같은 입력"은 Kafka 의 바이트 상태가 아니라
**원본 파일 수준에서** 성립한다. `PYTHONHASHSEED` 는 설정하지 않았고 회차마다 별도
프로세스라 문자열 해시 시드가 매번 달랐는데도 갈리지 않았다.

> 이 입력은 원본 영상 텍스트가 아니다. 저장소에 잡의 **입력**이 남아 있지 않아
> 산출물에서 재구성했다(키워드를 이어 붙여 title 로 씀). 키워드만 이은 문서는
> TF 동점이 원문보다 많아 상위 8개 선정의 동점 구간이 넓다 — **원문보다 불리한 조건**이다.

**③ 회차가 달라지면 결과가 달라진다. 원인은 코퍼스 의존성이다.**

②로 잡이 결정적임을 확인했으므로, **같은 575개 문서를 그대로 둔 채 코퍼스만**
575 → 1,365 로 키워 코퍼스 효과만 분리해 쟀다.

| 575개 공통 영상 기준 | |
|---|---|
| 완전 일치 | 107/575 (**18.6%**) |
| 집합 일치 | 182/575 (31.7%) — 순서만 다름 75 |
| 내용 다름 | 393/575 (**68.3%**) |

문서는 한 글자도 바꾸지 않았는데 68.3% 의 영상에서 키워드 구성이 바뀌었다.
배치 TF-IDF 라 **수집 규모가 바뀌면 IDF 가 통째로 바뀌기** 때문이다.
파이프라인 버그가 아니라 알고리즘의 성질이다.

저장된 회차끼리의 비교도 같은 방향이다 (입력이 서로 달라 코퍼스 효과와 분리되지 않는다).

| 비교 | 공통 영상 | 완전 일치 |
|---|---|---|
| 8차(575) ↔ 2025-04-30(350) | 122 | 13 (10.7%) |
| 8차 ↔ 2025-05-03(1,105) | 315 | **0 (0.0%)** |

여기에 "재현율 95%" 같은 목표를 쓰면 **달성 불가능한 목표를 적어 놓는 것**이 된다.
쓰려면 먼저 온라인 IDF 나 고정 코퍼스로 바꿔야 한다. 그건 설계 변경이고,
"이번 주에 유독 튀는 키워드"를 못 잡게 되므로 주간 트렌드라는 목적과 상충한다.
근거: [ADR-0010](adr/0010-reproducibility-scope.md)

### 조인 스큐 — 완화가 개선이 아니었다

1,296,229행 · 각 3회 p50 · `local[*]` · AQE 끔.

| 모드 | 조인 방식 | 총 소요 | 파티션 max/median |
|---|---|---|---|
| plain | SortMergeJoin | **44.44s** | 4.76 |
| broadcast | BroadcastHashJoin | 47.96s | 4.76 |
| salt (상위 5키 × 16버킷) | BroadcastHashJoin | 62.03s | **2.39** |

**salting 은 편차를 실제로 절반으로 줄였는데 총 소요가 40% 늘었다.**
2단계 집계(`collect_set` → `flatten` → `array_distinct`) 비용이 이득보다 컸다.

`explain()` 으로 조인 방식이 실제로 바뀐 것까지 확인했는데도 broadcast 가 8% 느리다.
키워드 쪽이 6,494행뿐이라 어느 쪽이든 셔플이 지배적이지 않다.

**이 규모에서 스큐는 병목이 아니다.** 그래서 스큐 목표치를 쓰지 않는다 —
줄여도 느려지는 지표에 목표를 거는 것은 의미가 없다. 근거: [ADR-0008](adr/0008-skew-not-mitigated.md)

> 단일 노드 기준이다. 실제 클러스터는 네트워크 셔플 비용이 커서 broadcast 이득이
> 클 수 있다. **"broadcast 는 쓸모없다"로 일반화하면 틀린다.**

### 그 외

| 항목 | 왜 목표가 없는가 |
|---|---|
| 클라우드 비용 | 로컬 단일 노드다 |
| 수집 신선도 | 주간 배치이고 연속 운영한 적이 없다 |
| 파이프라인 성공률 | 30일 운영 이력이 없다 |
| 메뉴 매칭 정확도 | 카페 메뉴가 **합성 데이터**다. 실제 분포라는 보장이 없다 |
